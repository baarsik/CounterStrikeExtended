# First-class custom weapons for CounterStrikeExtended

**Status** Proposed technical specification and user requirements. Source baseline `c591e0b6cf96fde9cc406891deb6d9f19487eb54`. The analysis covers Counter-Strike multiplayer and the `csextended` AMX Mod X module. It is based on source inspection.

## Decision

Allow a server operator to add `weapon_svd` as a distinct gameplay item. It has its own definition, runtime instances, ammo policy, selection name, presentation, and attribution. It can coexist with the AK-47 and with other custom weapons, subject to the server's normal equipment rules. A generic custom rifle implementation can serve multiple definitions. Registering a definition requires zero new C++ classes, fixed stock weapon IDs, or per-weapon client builds.

The proposed implementation consists of a **GameDLL weapon backend**, the **`csextended` AMXX module**, and a **CSE client** that understands a negotiated custom weapon protocol. The GameDLL owns gameplay and inventory. The module exposes the server API and orchestrates registration and network sessions. The client renders the state, submits selections, and plays authorized effects. The first delivery uses server-authoritative weapon simulation. Locally predicted presentation for supported behaviors is an additional milestone.

## How weapons work today

| Area | Current behavior and implications |

The engine's named-entity path resolves a classname to an initializer. A new `WeaponList` string alone never creates an entity or adds behavior. Adding a stock weapon sets a bit with `1 << m_iId`. Manual and death drops use stock ID lookups for world models and ammo metadata. An arbitrary new integer would reach stock shifts or array indexes unless those paths were changed. The shared runtime has 64 weapon-data slots and a six-bit slot index, but the shipped delta descriptions encode the active and weapon-data IDs in five bits. `usercmd_t` has a byte-sized `weaponselect` member for local selection. The shipped CS command delta omits it, and the HUD already sends selection to the server by name. Expanding one table or HUD message is insufficient. The killfeed resolves a string as a global `d_` sprite. Buy/rebuy, presets, and bot handling have stock assumptions and need explicit integration or a declared fallback. | CSE module | The current module deploys extended stats and server forms. It has no weapon registry, gameplay backend, or weapon natives. Forms provide a local precedent for map-scoped registration, per-client capability and readiness, and bounded synchronization. The weapon capability needs its own version and state. AMXX plugins can already give a stock entity distinct models, animations, ammo, or attacks for a tagged instance. For example, Hedgehog Fog's custom weapons API creates a named stock weapon, attaches a plugin marker, rewrites the receiving player's `WeaponList` row using the original numeric ID, redirects the custom command to the base classname, and manages stock prediction to prevent unwanted animations. To players this can look like a new weapon. Its implementation still depends on the base entity and a shared stock ID at the HUD/prediction boundary. This is an example of current practice, with individual plugins varying in their hooks and use of overrides. [Custom weapon creation and HUD publication](https://github.com/hedgefog/cs-modding-kit/blob/master/api_custom_weapons.sma#L1488-L1606), [command translation](https://github.com/hedgefog/cs-modding-kit/blob/master/api_custom_weapons.sma#L711-L725), [prediction handling](https://github.com/hedgefog/cs-modding-kit/blob/master/api_custom_weapons.sma#L1625-L1650)

ReAPI can give named entities and modify instance or global `ItemInfo`. The reviewed ReGameDLL API exposes hooks and weapon metadata access, while the weapon precache still populates a fixed table. These calls do not establish a general dynamic weapon-class registry. AMXX CSX's `custom_weapon_add` registers a stats identity. Its companion calls report shots and damage to the stats module. ## User requirements

| ID | Requirement |
| --- | --- |
| UR-01 | A server operator can install models and a versioned definition for `weapon_svd`, start a map, and enable the weapon without recompiling the client or GameDLL for that definition. Registration rejects duplicate keys and stock name collisions with a diagnostic that identifies the definition. |
| UR-02 | A plugin author can look up a definition, grant or spawn a weapon, query a player's actual custom weapon and ammo, equip or remove it, and receive lifecycle and combat notifications. Failures have documented reasons that allow the plugin to choose a fallback. |
| UR-03 | A player can acquire the new weapon by server grant or world pickup, select it by name or normal inventory controls, fire, reload, zoom if configured, switch away and back, and drop or recover it. A gun dropped by a player keeps its definition and remaining clip. Normal primary and secondary equipment restrictions still apply. |
| UR-04 | Two players can use the SVD and a stock weapon simultaneously. Two definitions in the same behavior family can also be active simultaneously. Acquisition, presentation, damage attribution, and ammo for each resolve to the correct definition and instance. If a server ruleset permits both in a single inventory, both rows remain independently selectable. |
| UR-05 | Players see the correct name, weapon selection and pickup icon, ammo counts, crosshair or scope, first-person and world-facing models, animations, sounds, and killfeed identity. Presentation remains usable if an optional icon or sound is unavailable. |
| UR-06 | Late joiners and in-eye spectators can see the correct weapon and permitted current state. New local CSE demos reproduce custom identity, presentation state and events from their recording, including a recording started after joining. Existing demos continue to load. |
| UR-07 | The operator can allow stock clients to join with stock-only equipment or require a weapon-capable CSE client. An old client receives valid legacy messages and can see the legacy-compatible world representation and a generic kill icon. Server options and failure messages distinguish unsupported versions from missing required resources. |
| UR-08 | An operator can use a plugin shop, for example via CSE server forms, to sell a custom weapon under normal purchase restrictions. The action returns a clear result and charges only for a completed purchase. Custom inventory works on servers with no shop. |
| UR-09 | A failed or malformed definition, stale selection, disconnect, round restart, or map change cannot remove a player's stock weapon by accident, duplicate an item or award, or leak one server's registry into another connection. |
| UR-10 | A weapon with a secondary ammo type shows the secondary reserve in blue above the normal rifle ammo row. Firing the launcher consumes only secondary ammo. Firing or reloading the rifle changes only the primary magazine and reserve. The SVD Custom fixture exercises both pools. |

## Architecture and deployment choices

| Approach | Result |
| --- | --- |
| Tagged stock weapon and HUD adapter | Deployable through server plugins on existing servers. Two players can see different presentations for instances of a stock class. Stock ID, entity, ammo, and prediction assumptions remain. Useful for maintaining existing mods and outside the first-class acceptance criteria. |
| Dedicated generic GameDLL weapon and negotiated CSE side channel | Proposed. A stock-independent weapon object shares audited game systems through an explicit backend interface. Existing GoldSrc formats continue carrying the stock game, models and normal input. Catalog and custom state use the extension. This requires a cooperating GameDLL and avoids per-weapon exports or a new global protocol. |
| Widen the core weapon protocol | Enables a different wire design, but requires coordinated engine, client, server, HLTV, demo and compatibility work. Wider fields alone still leave factory, gameplay and HUD work. No dependency on this approach for the proposed feature. |

Start with the in-tree CS GameDLL as the reference backend. Qualify **CSE Windows x86 dedicated server + in-tree x86 CS GameDLL + Metamod + AMX Mod X + `csextended`** first. Windows x86 is the current intersection of the in-tree runtime and standalone module targets. Use the pinned Win32 fixture's Metamod-R and AMXX versions as the initial loader candidates. Keep the unchanged ReHLDS fixture as a compatibility control. The in-tree combination still needs its own live qualification. [Runtime support](building.md#platforms-and-dependencies), [AMXX build guards](../cmake/AMXXModules.cmake#L1), [Win32 reference stack](../tools/qualification/fixtures/win32-server/README.md#L1)

Expose a small versioned optional interface callable by the module. Resolve it against the actual game module loaded beneath Metamod and verify that the provider matches the active game. Its contract covers definition registration and finalization, factory and lifecycle operations, a batch of authoritative state and gameplay events, resource availability, and per-client eligibility. Use fixed-width values, explicit version and size negotiation, opaque validated handles, and documented ownership and lifetime through the interface. Keep existing engine, client and GameDLL exported ABI tables intact. If discovery fails or the contract is incompatible, reject custom registrations with a diagnostic and continue offering the rest of `csextended`.

For Windows/Linux x86 deployments already using ReHLDS and ReGameDLL, the first-class path needs an equivalent cooperative ReGameDLL build or a separately qualified bridge covering that same contract. Existing ReAPI hooks are candidate integration points. A bridge on an unchanged GameDLL would have to own its own weapon implementation plus inventory, command, damage, and observer integration. Support for that deployment is unproven. Module-only installation on an unchanged stock GameDLL is available for legacy mod patterns, with no first-class guarantee. If an existing ReGameDLL deployment must be supported on day one, make backend qualification a release dependency before promising operator availability there.

### Definition, identities and limits

Use a canonical map-independent key such as `weapon_svd` in config, scripts, commands and logs. Use lowercase ASCII with the `weapon_` prefix, digits and underscores, at most 47 bytes for the full key. Reserve stock classnames and aliases. Optional purchase aliases use a separate validated namespace. Keep an independent display name, either bounded UTF-8 text or a recognized localization key with a literal fallback. Define three identities:

- **Definition ID** is an opaque, nonzero 16-bit number within a committed map catalog. Persist and log the canonical key for cross-map references.
- **Instance ID** is a nonzero 32-bit serial within the map generation. It stays associated with the same item across owners and drops. An AMXX entity index is optional auxiliary data. Instance operations validate both the serial and generation so an edict reused later cannot target a different weapon. V1 allows one owned instance per definition per player. Same-definition pickups follow the definition's duplicate pickup policy. Name-based selection is therefore unambiguous.
- **Ammo ID** is a separate typed, bounded identifier. A private reserve pool belongs to the player and is shared only by weapons that reference that pool. A definition may explicitly reference a stock reserve pool, whose existing stock maximum and indexing apply. Different definitions referring to a private pool must agree on its capacity. Clip ammo belongs to the instance.

The versioned definition includes:

| Group | Required fields and rules |
| --- | --- |
| Identity and inventory | Key, display text, behavior family, primary or secondary equip category, HUD slot and sort order, selection weight, droppable flag, and pickup/respawn policy. Equip category is a GameDLL rule. HUD position is presentation. Resolve ordering ties deterministically by canonical key. Follow standard one-primary/one-secondary policy in the reference ruleset. Reject or transactionally replace an occupied slot according to the grant policy. |
| Ammo | Primary ammo reference, capacity, initial clip and reserve grant, ammo pickup behavior, and replenishment policy. Specify whether a clip is present explicitly. Represent zero as an empty clip or reserve. A new ammo type can have its own reserve capacity, pickup model and HUD icon. Buying ammo is an explicit integration. |
| Gameplay | Versioned hitscan behavior with semi-automatic and automatic fire modes, fire cadence, magazine reload, equip timing, damage and range parameters, spread/recoil profile, movement-speed modifiers, and optional secondary zoom with explicit FOV stages. Specify draw, holster, dry fire, reload completion and cancellation; whether an interrupted reload commits ammo depends on its completion phase. Inherit normal rules for freeze time, death, defuse, friendly fire, armor, team restrictions, and damage attribution. |
| Presentation | Game-relative view, player and world model references, semantic animation roles and model sequence numbers, optional validated bodygroups, fire/dry/reload sounds, selection and pickup art, ammo and killfeed icons, and crosshair or scope profile. Declare optional effects such as shell and muzzle flash with defaults. Third-person and world appearance must be standard precached resources. |
| Purchase | Optional price, team availability and rule identifiers. A grant and a purchase are distinct API operations. Route purchases through GameDLL policy, including buy time/zone, team/map restrictions, affordability and slot policy. Treat charge and acquisition as one server operation. |

V1 supports map-scoped definitions, private/stock primary ammo and configurable hitscan firearms, including a scoped semi-automatic rifle. The SVD Custom fixture also requires a configurable alternate projectile mode and an independent private ammo pool. Arbitrary scripted projectiles, melee, or detachable modes require additional shared schemas and server behavior. Reject a definition using an unsupported behavior or feature. Proposed V1 caps are 128 weapon definitions and 128 private ammo definitions per map, 16 custom instances in one player's inventory, 16-bit unsigned custom clip/reserve counts with a separate no-clip flag, and 96 KiB of encoded catalog per map. Model, sound, event and resource availability may reduce the map's actual capacity. The client must display the supported ammo range without truncating values. Overflow is a specific registration or grant error. Never wrap IDs or replace existing definitions to make room.

For example, an operator registers `weapon_svd` with the scoped semi-automatic behavior, a primary equipment category, a 10-round in-game clip, an independent reserve pool, and custom presentation assets. A plugin grants one to a ready player or spawns it in the world. The player selects `weapon_svd`, fires twice and drops it. The next player picks up the same instance with eight rounds in its clip. Reserve ammo follows the configured pool and drop policy. A stock AK-47 elsewhere on the map retains its own identity, reserve and HUD entry. The numbers are illustrative and impose no balance requirements.

### GameDLL backend

1. **Factory and placement.** Implement one registered generic CS weapon entity that carries a validated definition identity and server behavior. The backend named factory resolves `weapon_svd` to this class, with the custom key retained as the item identity. Use the factory for grant, direct world spawn, and respawn. Support map placement through an exported generic classname with a `weapon_svd` definition key. If map entities are parsed before the server can finalize its catalog, defer activation until the binding is available. Unknown keys are diagnosed and removed. Literal BSP `classname=weapon_svd` and arbitrary legacy `CreateNamedEntity("weapon_svd")` require dynamic engine/Metamod classname resolution or a qualified dispatcher. These forms are follow-up integrations. Backend factory name lookup and normal player selection by `weapon_svd` are V1 requirements.
2. **Inventory and world.** Keep custom items integrated with the server's active/last item and GameDLL switching rules. Register explicit custom branches anywhere stock code assumes an ID, including duplicate handling, ownership bits, pickup notification, item info lookup, frame update, ammo, auto-switch, item stripping, manual/death drop, respawn and spectator update. Guard legacy-only paths by item type before array indexing and shifting. Keep `m_fWeapon`/HUD clearing and stock update delivery coherent across mixed inventory. A dropped item retains clip, serial, behavior and model. Pack reserve ammo only where the active ruleset permits it and account for shared reserve once. A map weapon may respawn from its template with a fresh instance ID. Audit `AddPlayerItem`, `RemovePlayerItem`, `CWeaponBox`, `GetNextBestWeapon`, and all consumers that assume weapon types or stock world model lookups.
3. **Simulation and attribution.** Route normal `IN_ATTACK`, `IN_ATTACK2` and `IN_RELOAD` to the active custom item through game rules and normal input timing. Use the existing server damage and trace paths with custom weapon attribution captured when the attack occurs. Reuse GameDLL model, animation, FOV and speed updates with deliberate restoration on holster, strip, observer transition and death. Use authoritative shot and action serials for presentation. Feed ordinary damage, scoring and death rules once. Publish a stable custom key in server logs, and expose it to plugins independently of the legacy death token. CSX registration/reporting and third-party stats integrations are optional adapters. Never assign a stock ID to get attribution.
4. **Clientdata boundary.** A custom weapon has no ordinary `WeaponList` row, weapon bit, `CurWeapon`/`WeapPickup` identity, or stock predicted object. Keep stock input, ownership bits and weapon-state deltas for real stock guns. Emit a neutral legacy active weapon value while custom is active, and publish custom active state separately. Ensure values left in legacy clientdata cannot start a stock attack or reuse stock ammo metadata. Preserve admissible movement state while the custom weapon is active. Sending a single clear on transitions to/from a custom weapon is part of the server/client contract.
5. **Rules integration.** Preserve stock bot and teammate behavior through pickup, equipment and next-best-weapon decisions. V1 can restrict bots to stock equipment and decline custom pickups/grants with a defined result. Bot purchasing, weapon-specific AI, stock rebuy/autobuy, career logic and native buy-preset editing are follow-ups. When a server enables custom weapons, CSE single-player save/restore is outside V1. Existing saves and non-Counter-Strike runtimes keep their existing data layouts. Future persistence needs canonical keys and a defined missing-definition policy.

### AMXX module and operator workflow

Add a weapon feature to `csextended` with its own lifecycle and configuration, alongside stats and forms. The module loads declarative definitions from `csextended/weapons/` under the configured AMXX data directory and accepts registration requests during a documented per-map precache phase. Both paths feed one backend registry and validation pipeline. Collect registrations, check cross-references and resource budgets, then seal the catalog before publication and world item activation. A successful submission means the definition is staged. Return a final status by key after the backend commits or rejects it. When a plugin registers a definition, record ownership and reject duplicate keys with both sources cited. Keep committed definitions immutable for the map. If a plugin unloads, remove its callbacks and retain committed declarative definitions until the next map. Reject registrations after precache and leave a usable stock map if the backend is unavailable. Failed definitions create no visible registry entry or gameplay item. If precaching has already consumed an engine slot, account for it for the rest of that map.

Freeze the registration window at a hook that runs after all Pawn `plugin_precache` submissions and while resource precaching is still legal. For the reference CSE engine, the GameDLL's `ServerActivate` callback runs before the engine enters its active state and writes the resource list. Qualify the exact Metamod callback order at milestone 1 before choosing the final hook. Verify the equivalent engine and AMXX ordering independently for ReHLDS. Preflight map-wide resource headroom using a qualified backend resource-count mechanism or a conservative measured bound before invoking precache calls that can abort map loading. [Activation order](../src/engine/sv_main.cpp#L2903), [precache failure behavior](../src/engine/pr_cmds.cpp#L1429)

The public Pawn contract covers the following operations. All mutation results describe success or a failure such as unsupported backend/client, wrong phase, missing definition, slot full, insufficient funds, invalid player or instance, blocked by game rules, or resource budget exceeded.

| Interface | Behavior |
| --- | --- |
| Register weapon and ammo, look up and query definitions | Accept a named definition asset or a versioned set of typed fields. Return submission errors immediately and a final status at catalog commit. Diagnostics identify the source and field. Lookup returns a map-scoped handle for a committed definition and the canonical key. |
| Query capability and readiness | Distinguish server backend availability, client protocol support, and per-map readiness. Provide a ready notification so plugins can grant a loadout after synchronization. |
| Grant, spawn, equip, drop, remove and enumerate | Return a validated instance handle where applicable. Grant copies no client-supplied data. Spawn accepts map coordinates through server-authorized scripts. Support reject, replace or drop-current policy where game rules permit it. Equip and remove verify owner and current generation. |
| Query state and grant ammo; purchase when enabled | Expose current clip, reserve, active state and ammo type. Clamp grants to the pool limit. Revalidate buy policy on the server even when a form has already rendered a buy button. Roll back acquisition/charge on partial failure and make a duplicate action request idempotent. |
| Lifecycle and combat notifications | Notify on spawn, pickup, deploy, holster, reload begin/complete, shot, drop, remove and attributed kill. Deliver read-only snapshots after the corresponding commit. Define dispatch order, avoid reentrant inventory mutation, and queue callbacks' gameplay requests at a safe frame boundary with handle revalidation. |

Package an operator guide, definition schema, sample SVD and a small Pawn example covering grant, spawn, selection/readiness, and shop purchase. Use the existing CMake module package and include files. A standalone module build targets Windows x86 and Linux x86. The reference GameDLL and CSE client qualification uses supported runtime combinations and requires a qualified backend/module pair before claiming a listen-server installation on a given platform. ### CSE protocol and assets

- **Negotiation.** Use a distinct versioned capability and server challenge tied to the current connection and map generation. Reuse the session pattern in forms where it fits. Capability is a compatibility signal. Validate every request independently. An unsupported client cannot acquire/equip custom weapons through grant or touch. Mixed-client mode allows that player to use stock weapons and receive ordinary precached world models/sounds and the legacy killfeed. CSE-only mode rejects an incompatible version at connect when detectable and keeps an unready client from active play until the catalog and required resources are ready or a bounded timeout occurs. Optional presentation resources use client defaults.
- **Catalog.** Send a reliable begin/chunk/end transaction with protocol version, generation, counts and catalog revision/digest. Include only data needed for display and client functionality. Validate and stage the full catalog, then commit it atomically and acknowledge that specific generation and revision. Define a bounded retry and timeout. An unknown or invalid definition never partially populates the HUD or becomes selectable. A join-in-progress client follows the same sequence. The server does not publish custom ownership or active state for that recipient until readiness, except the initial full snapshot that establishes the live state.
- **State and ordering.** Publish sequenced changes after server commits, with bounded full snapshots at readiness, resync, and observer-target changes. Include generation, recipient context, state sequence, owned instance-to-definition mappings, active and last item references, ammo pool counts and equip/reload/zoom state as needed. Scope player-only data to its owner. Send only authorized presentation and scoped active state for spectators. Deduplicate pickup and action events by serial. Clear the custom active state when selecting stock, dying or leaving an observer target. Reject stale generations, impossible references and out-of-order state; request a bounded resync when the current state cannot be recovered. Make snapshot and delta application atomic.
- **Commands.** Use a bounded namespaced selection request with generation and target instance, and route plain `weapon_svd` or `use weapon_svd` through the backend's name lookup. Validate that the request resolves to a current, owned and deployable item and that the player can switch. Wheel, fast-switch, last inventory and drop act on the same logical identity. Repeated requests must not redeploy or reapply effects unnecessarily. Existing user commands still carry attack/reload controls. Send no custom weapon IDs in the legacy numeric selection field.
- **Transport and effects.** Use bounded reliable user messages for catalog, authoritative snapshots, and important state transitions, with chunk payload below the 192-byte engine ceiling after framing. Pace per client and cap bytes, retry queues and requests. Use normal precached sounds/models and supported engine events where practical for remote players. Send transient presentation separately from reliable inventory state. Avoid a reliable message per bullet and give high-rate fire effects a bounded per-client budget. Where multiple paths can deliver an effect to one viewer, define one owner and deduplicate using shot/action serials. For killfeed, define exactly one row per death. Use a neutral legacy icon for unsupported clients and deliver custom attribution to ready clients through a single structured notice or an explicitly correlated replacement. Cover simultaneous kills and avoid matching by weapon name or timestamp alone. [Engine message limit](../src/engine/pr_cmds.cpp#L55), [HLTV message parsing](../src/HLTV/Core/Server.cpp#L2133), [stock event suppression](../src/engine/pr_cmds.cpp#L2392)
- **Resources.** Validate relative asset paths, permitted types, byte sizes, model/sprite/sequence bounds and resource counts at registration and on receipt as applicable. Precache models and sounds before server activation. In mixed mode, qualify optional model registration on the target engine and send an installed, precached fallback world/player model to recipients who lack the custom one. Unknown or legacy recipients use that fallback unless the server has reliable asset readiness evidence. Use built-in client art or a bounded, negotiated CSE transfer for optional HUD/scope art. Ordinary generic precaches and default model precaches can be map-wide fatal when files are missing. A resource registered that way must be declared a map admission requirement and cannot be treated as optional. Track file identity where the catalog requires an exact resource, and use scoped asset paths that cannot shadow stock content. A ready CSE client with downloads disabled may use verified local assets. Missing required weapon assets leave the player stock-only in mixed mode and block active play in required mode. Missing optional assets use defaults with diagnostics. If the map requires custom weapons and has no valid catalog, refuse that setup or switch to stock-only operation with an operator-visible reason. [Resource-list flags](../src/engine/sv_main.cpp#L1679), [optional model registration](../src/engine/pr_cmds.cpp#L1410), [client missing-model handling](../src/engine/cl_main.cpp#L518)
- **Reset.** Reset catalog, loaded handles, requests, effects and spectator state on new server/map generation or disconnect. Round restart invalidates obsolete instances, ammo and player state under GameDLL rules and retains the map catalog. Plugin reload does not mutate the published catalog. Demo playback builds its own registry from the recording and never sends a live readiness response.

The V1 wire contract has the following logical records. Exact byte layout and registered message names are implementation decisions. Use explicit little-endian integer encoding, length-prefixed variable fields, a message/schema version, and separate tags for absent, stock and custom references. Do not send native C++ structs.

| Record | Minimum contents and application rule |
| --- | --- |
| Session and readiness | Version, map generation, connection challenge, catalog revision and readiness result. The acknowledgement echoes the challenge and revision. A per-definition resource result identifies which weapons a client can use. In required mode all server-designated required definitions must be available. |
| Catalog | Transaction ID, counts, total bytes and digest; chunks with bounded offsets, decoded record types and lengths; end with matching transaction ID. Reject gaps, overlaps with conflicting contents, unknown required records and invalid dependencies. |
| Inventory snapshot or change | Generation, sequence and base sequence for deltas, view context, instance-to-definition entries, independent ammo counts, and active/last references. Chunk a snapshot across messages when needed and apply it after validation. Delta with an unknown base requires resync. |
| Active presentation and actions | Generation, subject/context, state sequence, active selection, view model/animation role, FOV stage, action serial and optional shot data. Keep private reserve data out of public action records. Only apply presentational actions to their matching context. |
| Client selection and resync | Generation, request serial and target instance where applicable. Return the accepted state or a documented failure. Rate-limit and require current readiness for instance selection. The client cannot submit shots, damage or ammo values through this channel. |

### CSE client integration

1. **Registry and inventory UI.** Add a custom registry and authoritative per-view state outside `WeaponsResource`'s stock ID arrays. Present a merged list with stable stock ordering, independent custom rows, and deterministic ties. Allow multiple display rows at one nominal slot/order where necessary. Support numeric slots, fast switch, inventory wheel, `lastinv`, name binds and drop. Custom selection may highlight pending intent and only changes the confirmed active weapon on a server state update. Display clip/reserve using extension counts, handle no-clip explicitly, and clear leftover stock ammo, selection and crosshair visuals on transitions.
2. **Models, reticle and effects.** Bind custom viewmodel and animation roles to the confirmed active definition. Resolve crosshair and scope from the definition and current zoom state instead of stock sniper ID switches. In-eye rendering uses the transmitted view model and scope state. Validate sequence/bodygroup indices against the loaded model and invalidate cached appearance when the definition changes even if two definitions share a model. Handle missing optional art/sounds with built-in generic assets. Support custom pickup and killfeed without inserting sprites into the global stock atlas by numeric ID. Preserve existing legacy HUD and ReGameDLL message variants when no custom session is active.
3. **Authority and prediction.** In V1, leave movement prediction running and suppress stock weapon simulation for the custom active interval. At the stock/custom boundary coordinate selection confirmation with authoritative frame identity so replay of pending commands cannot fire the previous weapon, restore a stale stock model or overwrite the new FOV. Use a per-frame marker tied to an authoritative update on the applicable backend, or demonstrate that the neutral active-state transition, replay gating and ordered custom snapshot satisfy the same contract. Exercise both transition directions with high latency, packet loss and `cl_lw` on/off. Custom deploy/fire/reload/zoom render on authoritative updates, so gameplay feedback will incur network latency. The server must include the local shooter in custom effect delivery, since the stock `FEV_NOTHOST` convention can suppress events based on `cl_lw`. Do not switch the user's global `cl_lw` setting. Later prediction can share a deterministic subset of the behavior schema and reconcile against server weapon state at a processed command boundary. It needs explicit per-command input, timers, seed, clip, ammo, mode and event deduplication. Pawn runs server-side.
4. **Observers and replay.** For direct in-eye view, replicate the target's allowed active instance/definition, model/animation, zoom and ammo policy. Invalidate it immediately on target switching or exit, so the old scope and clip cannot carry to the next target. For a local CSE demo, write a versioned catalog and relevant state bootstrap in recording startup using the existing demo record envelope, including when recording begins mid-map. Record later state and effects as they occur. Playback consumes the recorded generation without a server, and missing assets fall back to generic presentation. Do not alter existing demo layouts or expect old players to render new HUD elements. Full HLTV fidelity requires the proxy to receive catalog and public presentation state, retain a bootstrap for late viewers and recordings, and handle target changes without publishing private inventory. Qualify that path separately. Until then, HLTV uses the legacy-compatible world presentation and generic death notices. ## Delivery and acceptance

| Milestone | Exit criteria |
| --- | --- |
| 1. Backend feasibility | On the Windows x86 reference stack, spawn and grant a generic custom entity identified as `weapon_svd`. The V1 verification matrix also covers:

- **Definition and transport.** Duplicate keys, stock alias conflicts, malformed records, conflicting shared ammo maxima, out-of-range fields, missing assets, truncated/oversized messages, unknown IDs, reorder or duplication, stale generations, full limits, unauthorized selection and version mismatch. Assert bounded resource use and preservation of valid committed state.
- **Gameplay and lifecycle.** Partial and empty reloads, reload interruption by switch/drop/death, dry fire, zoom transitions, damage policy, grant to a dead or unready player, slot reject/replace, buy with insufficient funds, duplicate purchase, bone/animation fallback, two simultaneous pickups, team switch, round restart, map change, reconnect and edict reuse. Track exact clip/reserve, authoritative damage, money, and single ownership before and after each transition.
- **Prediction and presentation.** With packet loss and elevated latency, switch stock to custom and back while firing, zooming and reloading. Compare stock-only controls, custom authoritative state, and effect counts under both local prediction settings. Verify no ghost stock shots, stuck zoom, wrong model, duplicate killfeed rows or double sound. Cover late join, in-eye target swaps, already-active recording start, map transitions, and demo playback with an empty optional asset cache.

Release acceptance requires the independent gameplay identity, the operator and plugin workflows, and the stated compatibility behavior. Native client prediction for arbitrary server-defined behavior, support on an unchanged upstream GameDLL, full HLTV metadata, and new single-player save support are separate commitments.
